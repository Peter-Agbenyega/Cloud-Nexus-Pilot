`deployment.env.example` contains non-secret selectors. `private-config.example` documents separate mode0600 files under an approved `/etc/cloud-nexus-pilot` (directory0700). Do not execute/source the combined example. Values come from authorized secret management, never Git, CI artifacts or screenshots. Credentials: distinct administrator/migration, Auth login and REST authenticator; non-login anon/authenticated/service roles; server-only restricted service JWT for settlement. Only an administrator can grant a measured account allowance; migrations create no free/unlimited budget.

- DB has **no host port**, only the internal dedicated Compose data network.
- Auth/REST/admin health publish only127.0.0.1:54191/54192/54193. Auth and REST also join the dedicated API egress bridge. Docker29 does not materialize published ports for a container attached only to an internal network; REST needs this second bridge for its loopback API/admin bindings. This permits outbound network access from REST as well as Auth; the database remains data-only with no published port.
- Realtime retains Linux host networking with HOST127.0.0.1:3010 and trusted proxy127.0.0.1/32. No broad bridge trust is added.
- Same-guest Caddy is the only public application ingress on80/443. Administrative SSH is restricted to the approved management path. Firewall DB/internal ports from LAN/public access; inspect `ss -ltn` and Docker bindings.
- Vercel reaches only approved **public HTTPS identity/data and WSS realtime endpoints**. Do not point Vercel at private guest IPs. If policy requires a private-only backend, qualify an approved private connector before deployment; none is assumed here.
- No raw token/body/access logs in Caddy; Auth/REST log error level. Private Docker environment is still readable by the guest's Docker administrators: restrict that group and backup secret custody.

`verify_config.py --env <selector-file> [--target <allocation-record>]` is a read-only shape/permission check, **not** live identity, DNS, image security or release authorization. The optional target record requires productpilot, verified allocation, owner/date and non-shared guest ID. Without it, deployment remains blocked. Template/unresolved values intentionally fail.

## Fresh staging initialization (not executed on any guest)

Use the exact reviewed commit and immutable application image digest, pin DB/Auth/REST images after security review, and take the exclusive guest release lock for every transition (`flock -n /run/lock/cloud-nexus-pilot-release.lock ...`). 4. Start `auth rest`. GoTrue performs its own auth-schema migrations as the restricted auth owner. Verify local Auth health and PostgREST `/ready` on54193 before application migration. Signups default disabled; SMTP/email confirmation remain required, not autoconfirmed.

Applied checksum mismatch or an unreviewed existing002 schema without a ledger blocks automatic adoption. No source schema is silently marked applied. Use the reviewed source-baseline/adoption procedure after comparing a restored schema; never insert ledger rows merely to bypass a failure.

Startup prerequisites include reachable SMTP (if email auth is supported), compatible signing/JWKS plan, approved provider key and bounded budget, correct callback URL and current schema. ## Backup, isolated restore and rollback

Reserve a separate dedicated Pilot backup volume/destination with retention, encryption, capacity monitoring and independent key custody. Do not use the damaged/shared source storage mentioned in historical incidents. `backup.py` streams `pg_dump -Fc` directly into CMS encryption, verifies the independently selected recipient certificate digest, refuses unsafe output paths and records private hash/exit receipts. It never restores, drops a database, writes plaintext dumps or reports restore success. Run only inside the approved guest against its validated Pilot Compose project. Retain source config/signing/SMTP/provider secret-version identifiers separately in encrypted escrow; database dumps alone cannot restore identity signing.

```sh
python3 ops/pilot/backup.py --env /etc/cloud-nexus-pilot/deployment.env \
  --recipient /etc/cloud-nexus-pilot/backup-recipient.pem \
  --expected-recipient-sha256 INDEPENDENTLY_VERIFIED_CERTIFICATE_DIGEST \
  --output-directory /approved/pilot-private-backups
```

Before production recovery, decrypt an archive through the approved key custodian into a new private0600 file in an isolated environment. Verify receipt hash, recipient, release/schema/image vector and free space. Create a NEW database named `pilot_restore_<randomhex>` with template0; never `pilot` and never `--clean` against an existing database. With prepared compatible roles/extensions, restore using `pg_restore --exit-on-error --dbname <new-database>`. Start a separate isolated Auth/REST test instance pointing only to that restored database and separate test URLs; production services must not be repointed. Verify A/B ownership, transcript sequence/cursors, final guidance, exports, deletion-state absence, RLS/service permissions and signing configuration. Keep failed restores isolated for review. Only remove the specifically created disposable target after verification. Existing local backup26-check and restart169-event receipts remain dated evidence, not a new guest restore.

Rollback: stop admission, pause costly paths, preserve final events, drain/cancel bounded work, and switch only to the previous recorded **immutable** compatible app/realtime image and preview/config vector. Preserve schema/data; no automatic down-migration, old-dump restore or source deletion. If identity signing/config changed, restore a compatible verification overlap or use the reviewed re-login plan. A failed first deployment has no invented previous release. Record pending/current/previous image and config IDs before changing services, clear pending only after acceptance, retain previous artifacts/secret versions. Do not promote or prune while any mandatory schema-2 gate is pending.
